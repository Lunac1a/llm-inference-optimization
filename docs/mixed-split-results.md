# Mixed 按来源分段读取：试验结果

2026-09-18。**候选数值检查通过，但独立 kernel 慢了约 34%–47%，不采用。** 已按预先冻结的门槛停止，未启动完整模型延迟、容量或独立质量阶段，也未追加调参。

## 实际改动

原实现每个 K/V tile 都包含历史 FP8 与当前 BF16 的地址、掩码及选择逻辑。候选在同一个 GPU kernel 中将 tile 循环分成：

1. 完整历史 tile：只读 FP8 cache/scales。
2. 最多一个跨界 tile：沿用原来的双源掩码处理。
3. 完整当前 tile：只读 BF16 K/V。

三段保持原有 tile 顺序，连续更新同一份 M/L/acc，再做最终归一化。没有改 BLOCK_M=64、TILE_SIZE=32、缓存写入、FP8 格式、BF16 当前输入或生产 Decode 路由。

实现位于 `dual_source_kernel.py`，服务入口由 `chunked_hybrid.py` 的 `INFERENCE_MIXED_SPLIT_SOURCES=1` 控制。**开关默认关闭，原 mixed 路径继续作为默认；此次没有将失败候选启用。** 候选与原始完整源码分别保存在原始产物的 `candidate-source/`、`baseline-source/`，便于后续复查。

## 数值结果

20 个固定用例（10 组形状 × seeds 42/43）全部通过，覆盖零历史、单 token 输入、对齐/跨界、query 尾部、长历史、反序物理页和非连续 V。

| 检查 | 最坏结果 | 冻结门槛 |
|---|---:|---:|
| 原始/候选相对混合精度 FP32 数学参考的 max_abs | 0.0127831 | ≤ 0.02 |
| 原始/候选相对参考的 RMS | 0.00147076 | ≤ 0.002 |
| 候选相对原始输出的 max_abs | 0.001953125 | ≤ 0.002 |
| 候选相对原始输出的 RMS | 0.0000209349 | ≤ 0.0002 |
| 新代码关闭开关后与原始源码逐元素相等 | 20/20 | 全部 |
| 调用前后 cache 字节、当前 K/V 不变 | 20/20 | 全部 |

参考先按真实 FP8 页和 scales 恢复历史，再拼接当前 BF16，使用 FP32 causal attention。候选输出并非总是与原实现逐元素相同；它在预定误差范围内，不能据此宣称所有真实任务输出不变。

## 独立 kernel 性能

Qwen3-4B 对应的 32 query heads、8 KV heads、head_dim=128，current=2048。原始/候选各热身 5 次，20 对 AB/BA 交替 CUDA event 测量，每个样本连续调用 5 次取单次时间。下表为20个样本的中位数；不是模型首字延迟。

| 历史 tokens | 原始 kernel | 分段 kernel | 延迟变化 |
|---:|---:|---:|---:|
| 2048 | 3.176 ms | 4.258 ms | **+34.1%** |
| 8192 | 9.225 ms | 13.339 ms | **+44.6%** |
| 14336 | 15.304 ms | 22.463 ms | **+46.8%** |

三形状中位数比值的几何均值为 **1.4170**，高于进入模型阶段所要求的 ≤0.97；最坏比值 **1.4678**，也超过 ≤1.03 的退化上限。全部60对样本中，候选均慢于配对原始版本，因此不是只依赖一个异常中位数。

## 为什么流程更简单，却变慢了

以下是直接保存的编译记录，三个性能形状相同：

| 编译资源 | 原始 | 分段 |
|---|---:|---:|
| registers (`n_regs`) | 255 | 255 |
| spill 指标 (`n_spills`) | 6 | 14 |
| 每个计算块 shared memory | 49,536 B（48.375 KiB） | 65,920 B（64.375 KiB） |
| warps | 4 | 4 |
| PTX 文本大小 | 155,942 B | 328,166 B |

**事实：** 去掉纯来源 tile 中不需要的读取逻辑后，三段静态展开让编译出的代码更大，共享内存需求与 spill 指标上升，而且实测更慢。

**解释假设：** 三份专用循环复制了 dot/softmax/累积体，使编译器的资源分配与调度变差；更多共享内存和溢出可能抵消了简化地址、掩码与选择的收益。

**尚未证明：** 本轮没有测硬件实际 occupancy、带宽、缓存命中率或 spill 的运行时访存成本。因此不能认定某一个指标单独造成了全部退化，也不能宣称所有按来源分段的实现都会更慢。结论只针对本次单 kernel、三段静态展开候选。

用简单的话说：**每段需要考虑的情况减少了，但编译后的 GPU 程序更大、更占资源，最终得不偿失。** 不应仅因为源码流程更直观就替换当前实现。
